# rubberruler Implementation Guide

- Version: 1.2 (2026-10-19; the plan of MA-BBOB for 0.2.0, M10; version 1.1 of 2026-10-14; version 1.0 of 2026-09-29, translated into English and brought up to date with 0.1.0).
- What is built is in `spec.md` (the source of truth), and why in `decisions.md`. This document states the order of construction, where mistakes are likely, and how the result is checked.
- **[Verified]** marks a fact confirmed by actually running the code, with the date.

---

## 1. Order of Construction

The library was built in small stages, each depending only on the earlier ones. All stages were completed for 0.1.0. Each stage, and each later change, passes the checks of CI (Chapter 5) before it is committed.

| Stage | Built | Condition for completion |
|---|---|---|
| M0 | The skeleton of the repository (Chapter 5) | The checks pass with an empty package. CI is green |
| M1 | `_errors.py`, `_seeding.py` | `derive_seed` returns the test values of spec 6.1 |
| M2 | `_transformations.py` | ψ matches the test values of spec 6.3. ψ(0)=0, ψ(1)=1 (absolute error 1e-12), increasing, the identity above 1 |
| M3 | `_problem.py`, `_instances.py` | `bbob_instances`, `transform`, `Problem` (budget, record, the names of IOH). f̂_max matches the test value of spec 6.3 |
| M4 | `_performance.py` | One run, the handling of failures, PS and J, `measure_performance` (without a cache, parallel with joblib), the pre-check of the algorithms |
| M5 | `_features.py` | Sampling, the two kinds of preprocessing, `compute_features`, the pre-check of the extractor |
| M6 | `_prediction.py` | `fit_predictor`, `r2_score`, detection of a mismatched feature type, the pre-check of the predictor |
| M7 | `_card.py`, `_run_test.py` | `run_test` (the three pre-checks first), the card, the progress, the collection of warnings |
| M8 | `_cache.py` | The cache of runs, resumption, the identification of functions (3.5), connected to `measure_performance`. Ctrl-C saves and stops |
| M9 | README, `examples/quickstart.py` | The code of the README runs in CI with the smallest settings |
| M10 | MA-BBOB for 0.2.0 (spec 5.2, 5.4, 6.1 to 6.3; D45, D46) in `_instances.py`, `_transformations.py`, `_features.py`, `_performance.py`, `_card.py`, `_run_test.py`, and `__init__.py`; then the README and CHANGELOG.md | Every existing test passes, including the card of the README and the test values of BBOB. Only the tests of what spec 5.1 and 5.3 changed are updated: the eleven public names, the key `suite` of `result.config`, and `RunConfig` with `suite`. The test values of MA-BBOB in spec 6.1 and 6.3 match. Instance numbers above 2³¹−1 stop with a `RubberRulerError` on both suites |

After M9, 0.1.0 replaced tqdm with rich for the output on stderr (`_console.py`; 3.6), and `transform_objective` was added (`_objective.py`; spec 6.7; D43).

M10 keeps every path of BBOB as it is. Only two private helpers know the suite: one creates the ioh problem of an instance (`ioh.get_problem` for BBOB, `ioh.problem.ManyAffine` for MA-BBOB), and one returns the instance keys of spec 6.1, which the four places that derive seeds (ψ, f̂_max, the sample of the features, and the seed of a run) use. There is no class per suite. The defaults of each suite are written once and used by `bbob_instances`, `ma_bbob_instances`, `run_test`, and the card.

rubberruler is independent of the experimental code of the paper (D24). It is built from `spec.md` alone, without reference to the research code. Reproducing the paper is out of the scope of this repository.

## 2. Modules

```
src/rubberruler/
  __init__.py          exports exactly the 11 names of spec 5.1 in __all__
  _errors.py           RubberRulerError (with the helpers that build the three-line message)
  _console.py          the output on stderr with rich: messages, stages, and progress (spec 5.2)
  _seeding.py          derive_seed (spec 6.1)
  _transformations.py  ψ of the spline family and the construction of g
  _problem.py          Problem (the problem as one run sees it: budget, record, the names of IOH), the exception at the end of the budget
  _instances.py        ProblemInstance, InstanceSplit, bbob_instances, transform, f̂_max
  _objective.py        transform_objective (spec 6.7)
  _cache.py            the Parquet store of runs and the identification of functions (3.5)
  _performance.py      one run, PS, J, measure_performance, the pre-check of the algorithms
  _features.py         sampling, preprocessing, compute_features, the pre-check of the extractor
  _prediction.py       FittedPredictor, fit_predictor, r2_score, the pre-check of the predictor
  _card.py             the text of the card and its rich panel
  _figure.py           the figure of the answer (spec 3.4: the bar chart of R² in PNG and SVG)
  _run_test.py         run_test, RubberRulerResult, the stages and the warnings, the writing of the figure
```

- Each module imports only modules above it in this list. Only `_run_test.py` combines all of them.
- A pre-check (spec 5.5) lives in the module that uses the checked component (there is no module only for checks). Each component function checks its own inputs, and `run_test` calls the three checks together before the heavy computation.

## 3. Verified Facts and Pitfalls

### 3.1 ioh

- [Verified] `ioh.get_problem(fid, iid, dim, ioh.ProblemClass.BBOB)` also creates iid 110 and 5000. `optimum.y` gives f_min. The bounds are [−5, 5]. A two-dimensional array evaluates several points together and returns a list.
- [Verified] ioh has no `__version__`. `importlib.metadata.version("ioh")` is used.
- [Verified] The wheels of ioh 0.3.22 (the latest) cover only CPython 3.9 to 3.12 on Linux x86_64, macOS, and Windows. On 3.13 and later and on Linux aarch64, pip builds from the sdist. On GitHub's ubuntu-latest (with gcc and CMake), the build took 281 seconds on 3.13 and 227 seconds on 3.14, all tests passed, and the values of the specification and the card were the same as on 3.12. On linux/arm64 of python:3.12-slim without a compiler (QEMU), the build stopped after 164 seconds with a CMake error (`Failed building wheel for ioh`), without saying that a compiler is needed (evaluation of 2026-10-01). With build-essential and cmake installed as the README says, pip built ioh on linux/arm64 (QEMU) of python:3.12-slim-trixie too (22 minutes under emulation; apt-get took 75 seconds), and `import rubberruler` worked (psutil from its aarch64 wheel; 2026-10-01). Python has no upper bound (D34).
- [Verified] ioh 0.3.17 and 0.3.18 require numpy<2, and 0.3.19 and later require numpy>=2. The pflacco environment (NumPy 1.24) receives 0.3.18 (Shuhei, 2026-09-30).
- [Verified] The Windows wheel of ioh (`iohcpp.cp312-win_amd64.pyd`) imports MSVCP140.dll without bundling it (NumPy, pyarrow, and scikit-learn bundle renamed copies). On Windows without the Visual C++ Redistributable (Shuhei's PC), the Python of python.org and the Python of uv have only vcruntime140.dll, so `import rubberruler` stopped with `ImportError: DLL load failed while importing iohcpp`. GitHub's Windows runners have it, so CI does not show the error (evaluation of 2026-10-01). `_instances.py` turns an ImportError whose message contains `DLL load failed` into a three-line ImportError that states what to install (spec 5.6).
- [Verified] MA-BBOB: `ioh.problem.ManyAffine(instance=i, n_variables=d)`; there is no `ProblemClass` for it, and `ioh.get_problem` cannot create it. The details (how ioh derives the instance from i, the clamp that makes `optimum.y` the exact minimum, the identity of the values across ioh 0.3.17 to 0.3.22, and the cost of evaluation) are in D45 (2026-10-19). Creating one MA-BBOB problem takes about 0.6 ms (0.03 ms for BBOB), which is negligible because a worker creates one per task (3.3).
- [Verified] ioh accepts instance numbers up to 2³¹−1 and raises a TypeError of pybind11 for 2³¹, on both suites (D46).
- Not yet verified: whether MA-BBOB gives the same values on Windows and macOS as on Linux. ioh draws MA-BBOB with the same bbob2009 generator as BBOB, whose values are the same on these systems, but the values of MA-BBOB have not been compared (Shuhei, 2026-10-20: recorded as open, not a condition of M10).
- The problem objects of ioh are kept inside `Problem` and `ProblemInstance` and are not shown to the user.

### 3.2 The Exception at the End of the Budget

- [Verified] An exception that derives from `BaseException` passed unchanged from the objective function to the caller in SciPy's Nelder-Mead, Powell, and differential_evolution, in pycma's `fmin2`, and in Nevergrad's CMA.
- Every call after the budget is exceeded raises the exception again. Even with an optimizer that swallows exceptions, the result is correct, because only values within the budget are recorded.
- If the budget runs out in the middle of a batch, the points up to the remaining budget are evaluated from the front and recorded, and then the exception is raised.
- An algorithm that stops before spending the budget, such as L-BFGS-B, is left as it is (the smallest value seen is recorded). Restarts are the responsibility of the user's algorithm.

### 3.3 Parallelism and Reproducibility

- [Verified] The tasks of joblib (loky) run in the main thread of a worker process.
- One task holds the n_runs runs of one pair (instance, algorithm) (sending about 270,000 runs one by one makes the cost of transfer noticeable).
- The workers apply `threadpoolctl.threadpool_limits(1)`. The equality of `n_jobs=1` and `n_jobs=2` is tested.
- NumPy does not guarantee that the random streams of a `Generator` stay the same across versions (NEP 19). Only the calls in the table of spec 6.1 are used for random numbers. If an upgrade of NumPy, SciPy, or ioh changes the test values of the specification, the change is treated as one that can change the answer (spec 7.3).
- The pre-check of "can it be sent to another process" imports and uses `cloudpickle` directly (the same library that loky uses to send tasks to workers). Because of the direct import, the dependency `cloudpickle>=3.0` is stated. joblib 1.6 depends on cloudpickle>=3.0, so the installed packages do not change. It is not used for the identification of the cache (3.5).
- [Verified] joblib 1.6 (2026-08-31) has no `joblib.externals.cloudpickle`. cloudpickle is no longer bundled; joblib depends on cloudpickle>=3.0 instead.
- When the runs end, the workers of joblib are closed at once (`get_reusable_executor(reuse=True).shutdown(wait=True)`). joblib keeps the workers for 300 seconds for the next call, during which they held memory even while the features were computed (3.6 GB in total for the small settings of the README on 24 CPUs) and, on Windows, kept the working folder in use (evaluation of 2026-10-01). Each worker watches the parent process that sends it tasks every second (`os.getppid()` on POSIX, psutil on Windows) and exits when the parent is gone. [Verified] After `kill -9` of the parent, 24 workers were still waiting for the lock of the queue that sends results after 600 seconds (the same with the idle timeout of loky set to 10 seconds, because they wait on a write, not on a task). With the watch, they disappeared within 1 second, and on Windows within 1.1 seconds after the parent was terminated forcibly. Right after a normal end, no workers remain (Linux and Windows). The resource tracker of loky (one process of 46 MB) remains until Python exits, so on Windows its working folder can be deleted only after Python exits (2026-10-01).
- [Verified] On Ctrl-C, loky removes the tree of workers with psutil and falls back to `pgrep` without psutil (`loky/backend/utils.py` of joblib 1.6.0). In an environment with neither psutil nor `pgrep` (python:3.12-slim), the fallback `process.kill()` after `FileNotFoundError: 'pgrep'` fails with `AttributeError: 'Popen' object has no attribute 'kill'` (the Popen of loky has no kill), and the thread that reads the results (ExecutorManagerThread) stops with it. The workers try to send results that are never read: one blocks on the write to the pipe, and the others on the lock of that write (they are not idle, so the idle timeout of 300 seconds does not end them). At exit, `_exit_function` of multiprocessing joins the workers and waits forever (2026-10-01, confirmed with py-spy; 25 workers remained after 420 seconds). With psutil as a dependency, the process stopped 0.3 seconds after Ctrl-C even without procps, and no workers remained after 2 seconds (the same as with procps; D39). On Windows (uv's CPython 3.12), it stopped in 0.8 seconds, and no workers remained (2.1 seconds with taskkill without psutil). On the side of rubberruler, stopping closes the generator of joblib so that the cancellation of joblib starts at once. The UserWarning of joblib that "some finished tasks were not used" suggests changing the input and is misleading, so it is suppressed while closing (the "stopped" line states the number of saved runs).

### 3.4 Transformation

- [Verified] Drawing 2000 transformations by the steps of 6.3 gives a median of max |ψ(z) − z| of 0.216.
- [Verified] The difference from the continuous integral is at most 3.9 × 10⁻⁶. The discrete steps of spec 6.3 are the definition (the continuous integral is not used).
- [Verified] Evaluating PCHIP takes about 3.7 µs for one point and about 100 µs for 1000 points together, which is negligible compared with the evaluation of BBOB.
- In the definition of the paper, g is the identity outside [0, 1], but z < 0 is clipped to 0 (spec 6.3). On BBOB, f ≥ f_min, so z < 0 occurs only by rounding, and clipping keeps the argument of ψ in its domain. `transform_objective` follows the formula of the paper instead (spec 6.7; D43).

### 3.5 Cache

- [Verified] The inner function returned by `make_es(sigma)` has the same source for different sigma. Identification by source alone returns the results of another sigma.
- **The identifier of a function** (per algorithm) is the hex of `hashlib.blake2b(digest_size=16)` over the following elements, turned into bytes by the rules below.
  1. The key in the dict of the portfolio.
  2. The source of the function (`inspect.getsource`), its default values (`__defaults__`, `__kwdefaults__`), and the values of its closure cells. For `functools.partial`, the inner function and `args` and `keywords`. For a callable object, `type(obj).__call__` and the `__dict__` of the instance.
  3. The values of the global names that the function refers to (`__code__.co_names` and the `co_names` of nested code objects) that exist in `__globals__`.
- **Global values**: a user's function (defined in a file that is neither in the standard library nor in site-packages nor in the folder of a distribution installed by an installer) is identified recursively by the same rules for 2 and 3 (a function seen once is skipped). Modules and the functions and classes of site-packages or the standard library contribute only the name of the top-level package and its version (`importlib.metadata.version`; the version of Python for the standard library). A change of a helper function or of the version of a library thus triggers a new computation. A user's class (one that appears as a global or closure value, such as a class that wraps a problem for another library) is identified by its base classes and the values of its namespace: functions as the user's functions, staticmethod, classmethod, and property by their inner functions. The source of a class is not used (up to Python 3.12, inspect looks for the source of a class in the file of `sys.modules[__module__]`, which is not found after runpy). [Verified] Classes were previously skipped as unidentifiable, so all three algorithms of the pymoo example triggered the warning "cached by name and source only" (2026-09-30). [Verified] A function whose `__module__` is `__main__` is always a user's function. Its file is looked up in `sys.modules["__main__"]` at that moment, so identifying, later inside `python -m pytest`, a function of a script run with runpy found `__main__` reverted to pytest in site-packages, mistook the function for a library, changed the identifier, and missed the cache (2026-09-30).
- **Libraries**: besides the standard library and site-packages, files inside the folder (`locate_file("")`) of a distribution installed by an installer (with RECORD and not editable according to direct_url.json) are libraries. [Verified] Previously, only site-packages was considered, so libraries installed with `pip install --target` and PYTHONPATH, or in the layered environment of `uv run --with`, were read recursively as the user's code, reached built-in functions, and gave the warning "cached by name only" for DE and Nelder-Mead of the quickstart (evaluation of 2026-10-01). Distributions installed as editable and those without RECORD (`setup.py develop`) remain the user's code (a change of their source triggers a new computation). A module whose file is outside the folder of the distribution is the user's code, even with the same top-level name (a local file with the same name).
- **Encoding of values**: a fixed form per type (neither pickle nor cloudpickle, because the same value can give different bytes; D22). `None`, `bool`, `int`, `float`, `str`, and `bytes` as the type name and `repr`. `numpy.ndarray` as dtype, shape, and `tobytes()`. NumPy scalars as dtype and `repr`. `list` and `tuple` element by element in order, `dict` sorted by key, and `set` and `frozenset` as the sorted encodings of their elements. Functions by the rules above. Any other value cannot be encoded: it is skipped and counted in the warning "name and source only" of spec 5.6.
- [Verified] `inspect.getsource` fails on built-in functions such as `max`. A function without available source is identified by its name (and the version of its package) only and is counted in the warning "name only".
- The key columns: instance_id, master seed, algorithm name, identifier of the function, budget, run number, version of ioh, and version of the cache format (`CACHE_FORMAT` in `_cache.py`; raised by a change that alters the values of runs, such as the derivation of the seeds of runs, so that old runs are not used; spec 7.3). The value columns: the smallest value, the number of evaluations, whether the run failed, and the message of the failure (short).
- Only the parent process writes. Each task writes a Parquet file with a unique name under a temporary name and moves it into place with `os.replace`. Reading uses a pyarrow dataset, and duplicate keys are dropped. No lock is needed.

### 3.6 The User's Components

- Static type checks: [Verified] in pyright, `Callable[[Problem], object]` accepted functions that return `None`, functions that return values, and lambdas. An extractor that returns an array instead of a `dict` was an error.
- [Verified] With a predictor annotated as a `Protocol` with positional-only parameters, the `Pipeline` of scikit-learn 1.9.1 was judged not to match (because `predict` is an `available_if` descriptor). The predictor parameter is therefore `object`, and the predictor is checked at run time.
- Copying the predictor: `sklearn.base.clone` if it has `get_params` (scikit-learn is used only if it can be imported), and `copy.deepcopy` otherwise. If the class itself (`RandomForestRegressor`) is passed, the error asks for parentheses, as in `RandomForestRegressor()`.
- If the predictor fails on features with NaN, the original exception is kept in `__cause__`, and the message gives the number of NaN values and suggests a `Pipeline` with `SimpleImputer`.
- [Verified] With pandas 3, `DataFrame.to_numpy()` can return a read-only array; passed as it is, the X and y that the predictor receives are read-only (PyTorch warns, and predictors that modify them in place fail). A writable copy is passed on every call (spec 4.3).
- [Verified] Features that differ by rounding (spec 6.6; D38): the skewness of the rank-based y of the quickstart is mathematically 0 on the instances without ties (2,760, all except f7), but takes scattered values of about ±1.3 × 10⁻¹⁵. Between NumPy 2.4.6 (Python 3.11) and 2.5.3 (3.12), 2,546 of 2,880 instances differed by up to 9.8 × 10⁻¹⁷, and R² of the random forest for rank differed in the third decimal place (the value of 3.11 on CI was reproduced on the development machine). The value-based features also differed by about 10⁻¹⁵, but their values are spread out, so R² was identical to the last digit. Merely permuting the noise of the skewness between instances changed R². scikit-learn's trees convert X to float32 and do not split between values closer than 1e-7, but the order of the values matters. The noise of the kurtosis collapses to one value in float32 and had no effect. After the fix, the tables of 3.11, 3.12, and 3.14 were identical to the last digit (2026-10-01). Whether to unify follows the formula of `math.isclose` (`|a − b| <= max(rel_tol × max(|a|, |b|), abs_tol)`). For arrays, the formula is written out instead of using `numpy.isclose`: `numpy.isclose(a, b)` computes `|a − b| <= atol + rtol × |b|`, which is not symmetric in a and b and adds the two tolerances, so its results differ from `math.isclose`.
- [Verified] `NGOpt` of Nevergrad 1.0.12 fails with NumPy 2.5. Its internal meta-model tries to convert a one-element array with `float(model.predict(...))` and raises `TypeError`, and the results changed even with the same seed. Nevergrad's `CMA` and `DE` work and are reproducible. The example in `examples/README.md` uses `ng.optimizers.CMA`.
- [Verified] With the algorithms of pycma, Nevergrad, ModularCMAES (CMA-ES and IPOP), and ModDE from `examples/README.md` in one portfolio, a pandas extractor, and a PyTorch predictor, `run_test` with small settings (d = 2, training 11 to 15, test 1 to 3, `budget_per_dimension=50`, `n_runs=3`) gave an answer without failed runs. The example with GradientBoostingRegressor that followed also returned R² (python:3.12-slim, Python 3.12.14, NumPy 2.5.3, SciPy 1.18.1, scikit-learn 1.9.1, cma 4.5.0, nevergrad 1.0.12, the CPU build of torch 2.14.0, modcma 1.2.0, modde 0.0.4; 2026-10-01). The "versions checked" in `examples/README.md` come from this run and from the pflacco environment of CI (Python 3.11). Nevergrad's `CMA` then emitted pycma's `InjectionWarning` (orphanated injected solution) on some BBOB functions (at d = 2: f1, f2, f5, f7, f11, f13, f15, f17; frequently on f5). Applied directly to f1 and f5 of ioh, without rubberruler, it appeared regardless of how the budget ended (the budget of Nevergrad or BaseException) and of the seed, so it comes from Nevergrad and pycma. The example with pycma's `fmin2` did not emit it.
- [Verified] Output on stderr with rich (`_console.py`, since 6f8b554 of 0.1.0; it replaced tqdm): in a terminal or a notebook, rich draws a spinner, a bar, and a check mark per stage; elsewhere, a stage writes plain lines when it starts, at most every 30 seconds, and when it ends. `RUBBERRULER_NO_PROGRESS` with any value except `0` hides the bars. When the console encoding does not start with `utf`, the spinner is `line` (ASCII), the bar is ASCII, and the check mark is a space. `tests/test_console.py` fixes these behaviors, including a strict cp932 terminal. The interval of 30 seconds in a log file comes from the evaluation of 2026-10-01: with tqdm, every update was written, and the log of P1 grew to 144 KB; the first-reader test then found that tqdm's `mininterval` alone wrote every 10 to 20 seconds because of its monitor thread (`maxinterval`), which was fixed before rich replaced tqdm.
- [Verified] The `rng=` of SciPy's `differential_evolution` exists from 1.15 and not in 1.10. `seed=np.random.default_rng(s)` works on every version and gives exactly the same result as `rng=s` (on SciPy 1.17.1 and 1.18.1, the same fun and nfev, without warnings). `seed=s` with an integer creates a RandomState and changes the random stream. The types of 1.15 and later list only `rng`, so pyright reports `seed=` as an error. The `seed=rng` line of the quickstart previously had `# pyright: ignore[reportCallIssue]` (2026-09-30), but the code of the README carries no comments for tools, so `executionEnvironments` in pyproject disables `reportCallIssue` for examples/ only (D41).
- [Verified] The DE of the quickstart passes the range as `Bounds(problem.lower_bounds, problem.upper_bounds)`. `differential_evolution` of SciPy 1.10.1 and 1.17.1 turns `Bounds` into a sequence of (lb, ub) pairs with `new_bounds_to_old`, then into the same array `self.limits` as for a sequence of pairs, and does not use `Bounds` afterwards. The behavior is therefore the same as with a sequence of pairs (the former `list(zip(..., strict=True))`) for every budget (2026-10-01).
- [Verified] `c_maes.utils.set_seed` of the C++ version of modcma 1.2.0 accepts only seeds below 2³¹ and raises TypeError for 2³¹ and above. Seeds of runs lie from 0 to 2³²−1, so passing them unchanged makes about half of the runs count as failures. `examples/modular_ela.py` passes `problem.seed % 2**31`.
- [Verified] The seven feature sets of pflacco 1.2.2 (55 features without `.costs_`) raise no exception and give no NaN on any of the default 2,880 instances at d = 10 with 500 points. However, `ela_meta.quad_simple.cond` divides by zero on 14 value-based instances of the linear function f5 and becomes infinite, and scikit-learn's random forest does not accept infinity. rubberruler converts infinity to NaN on receipt (D30), and the example fills it with a `SimpleImputer` Pipeline. At d = 2 with 100 points, `calculate_ela_level` raises an exception on 25 instances of f7 (the steps create many ties, and the quantiles have too few points), and 18 rows have NaN (2026-09-30, confirmed in the pflacco environment).
- [Verified] The features are computed in order in the parent process, so with ELA (about 0.5 seconds per instance at d = 10 with 500 points), the features alone take about 50 minutes with the default settings. `examples/modular_ela.py` with small settings at d = 10 (training 11 to 15, test 1 to 3, `budget_per_dimension=100`, `n_runs=5`; 264 instances, 5,280 runs) took 3 minutes 23 seconds in total in Docker on an i7-13700F (24 CPUs): 4 seconds for the runs and 3 minutes 15 seconds for the features (528 calls, 0.37 seconds each) (2026-10-01). The "about 3.5 minutes on 16 cores" of `examples/README.md` comes from this measurement.
- [Verified] pymoo 0.6.2 passes solutions together with shape (n, d), so `out["F"] = problem(X)` in `_evaluate` of a subclass of `pymoo.core.problem.Problem` suffices. For a batch that exceeds the budget, `problem` records only the points within the budget and ends the run (spec 4.1). One run of 10,000 evaluations at d = 10 took 0.27 seconds for GA, 0.38 seconds for PSO, and 0.42 seconds for Nelder-Mead on the development machine (about 0.9 seconds on Shuhei's PC), more than ten times as long as the C++ version of modcma. Seed 2³²−5 works too. pymoo's CMAES stops on its own criteria before spending the budget (about 2,300 evaluations; Shuhei, 2026-09-30). [Verified] `from pymoo.optimize import minimize` overwrites SciPy's `minimize` of the quickstart, and in the test that runs the code of the README in order, the Nelder-Mead of the quickstart failed. pymoo's function is imported as `pymoo_minimize`.
- [Verified] DeepELA (github.com/mvseiler/deep_ela, MIT) is not on PyPI. Its setup.py has the name `pflacco` and version 1.2.2; installed with pip, only the code (88 KB) is installed, without the trained models. The install.sh of the repository removes pflacco and installs DeepELA into the latest pflacco from GitHub. The folder `deep_ela` of the repository is closed under relative imports and contains the models, so the fetched folder on PYTHONPATH works with `import deep_ela`. It imports only torch, lightning, einops, and PyYAML (glob2 and tqdm in requirements.txt are not used). Fetching one commit with `git fetch --depth 1` takes about 80 MB (four models; the whole history is about 140 MB). The last four commits of 2026-09-02 changed how the coordinates and the objective values are passed and how the stride is handled, which changed the features, so the commit is pinned to c0368677461f96a17536111ee947bf111e8b8425 (Shuhei, 2026-09-30).
- [Verified] The medium model of DeepELA (num_df = 6) raises ValueError at d = 10. The large model (num_df = 12) arranges the coordinates and the objective value in 12 slots, so it handles d ≤ 11. ### 6.3 Steps to Release a Version

The English documents (formerly step 1: CLAUDE.md and the md files of docs/ in English, with English as the source of truth from then on) were completed on 2026-10-14. The absolute URLs of the images and the push trigger of `macos.yml` (formerly step 2) are in place as of 0.1.0.

1. Before the repository is made public, archive the history before 0.1.0 and delete its branches from origin. That history contains the design documents in Japanese (its commit messages are in English; checked on 2026-10-14). As of 2026-10-14, its branches on origin are `readme`, `review`, `usability`, `followup`, `deepela`, and `transform-objective-docs`; the history of main starts at the commit "First release: rubberruler 0.1.0" (49af2de).
   1. Fetch everything and list the branches of the old history again, since new ones may exist: `git fetch origin`, then, for each remote branch, `git merge-base --is-ancestor 49af2de origin/<branch>` fails for a branch of the old history.
   2. Write all refs, including the remote-tracking branches, into one file, and check it: `git bundle create rubberruler-history-<date>.bundle --all`, `git bundle verify rubberruler-history-<date>.bundle`, and `git bundle list-heads rubberruler-history-<date>.bundle`, which must list every branch of step 1. Keep the file outside the repository; it holds the only copy of the old history (including the sources of the figures; 3.10).
   3. Delete the branches from origin: `git push origin --delete readme review usability followup deepela transform-objective-docs` (with the list of step 1). `git ls-remote --heads origin` then lists only branches of the new history.
   4. Delete the same branches locally (`git branch -D ...`). GitHub can keep the commits of deleted branches reachable by their SHA for some time; only GitHub Support can remove them at once.
2. Before the first version, make the repository public. Check the README with "The appearance on PyPI" of 6.1, now with the images displayed. The job of `macos.yml` then runs on every push (public repositories do not use paid minutes).
3. Raise `version` in `pyproject.toml`, write the entry of the version in CHANGELOG.md (a change that can change the answer starts with **Can change the answer**; spec 7.3), pass the checks of Chapter 5, commit, and push to main. Wait until CI is green.
4. Create and push the tag: `git tag v0.1.0` → `git push origin v0.1.0`. The tag is `v` followed by the version in pyproject.
5. The workflow of publishing runs. Its build job fails if the tag differs from the version in pyproject. It then runs the checks of CI and `uv build` and stores dist as an artifact. The publish job uploads to PyPI with `pypa/gh-action-pypi-publish` inside the environment `pypi`.
6. Check the version and the display of the README at https://pypi.org/project/rubberruler/.
7. Create a Release from the tag on GitHub. If Zenodo is connected, it issues a DOI; add `doi` to `CITATION.cff` and commit.
8. Once the paper is published, add it to Citation in the README and to `CITATION.cff` (`preferred-citation`).
