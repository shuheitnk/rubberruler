# rubberruler Decision Record

The decisions made, with their reasons. They are not reconsidered during implementation. A change is confirmed with Shuhei, and this document and `spec.md` are revised first.

Format: **Decision** / Reason / Alternatives not chosen.

Notes in brackets that start with "As of 0.1.0" describe how the repository changed after a decision was made; the decision itself is unchanged unless a later decision revises it.

---

## Purpose and Scope

**D1. The library answers one question only: "should value or rank be used?"**
Reason: a single question makes it clear when to use the library and reduces what the user has to remember (the Simple principle of Made to Stick, and "omit needless words" of The Elements of Style).
Alternatives not chosen: comparison of several extractors, diagnostics per feature, breakdowns by function class, output in LaTeX.

**D2. The functionality is the necessary minimum. There are 9 public names (10 since D43, 11 since D45).**
Reason: more functionality takes longer to understand. It also keeps the implementation simple.
Alternatives not chosen (in earlier designs and removed): the presets `scale="full" / "quick"` and `rr.Config`, `dry_run`, `verbose`, `multi_output`, `sampling`, `on_feature_error`, `on_budget_exhausted`, `run_timeout`, `rr.check_setup`, `rr.demo`, the precomputed data `rr.datasets.paper_portfolio`, `rr.predictor_from`, `rr.export_samples` / `rr.import_features`, `rr.cache_info` / `rr.clear_cache`, `rr.plot_transformations`, `result.plot` / `save` / `to_dict`, the selector `FittedPredictor.select`, and subclasses of the exception (`SetupError`, `ConfigError`).

**D3. The user's only task is to match three input and output types (spec Chapter 4). Each input has exactly one type.**
Reason: with one way to write each input, there is one thing to remember. Fixed types let static checks and pre-checks find mistakes early.
Alternatives not chosen: injection of arguments by name, lists of extractor functions, factories of predictors, and `predictor_from`. A function of another form is wrapped by the user in a one-line lambda.

## Content of the Test

**D4. The answer is the feature type with the larger R² on the transformed test instances (τ* of the paper). A tie selects rank. The degradation is for reference.**
Reason: the rule of the paper. The degradation does not decide because the degradation of rank can be 0 by construction. A tie selects rank because rank-based features do not change under the transformation, so nothing is lost.

**D5. When the difference of the R² values is below 0.01, the answer is still given, and the card adds one line stating that the answer is weak.**
Reason: estimating a spread by repetition multiplies the computation by K and adds arguments. It does not fit the purpose of answering with the least effort.
Alternatives not chosen: repeating K times with different seeds of the predictor and reporting the spread of R².

**D6. J is the mean probability of superiority. On a transformed instance, it is computed from the values that the algorithm saw (the transformed values). Ties have no tolerance. A run that fails without any evaluation gets +inf.**
Reason: the quantity of interest is the performance on the transformed function.

**D7. The only transformation family is the spline family. The steps and the order in which random numbers are drawn follow spec 6.3. There is one transformation per instance.**
Reason: to measure with the same transformation family as the paper. The transformation is not a source of random variation (it is fixed to one).

**D8. The defaults are the settings of the paper: d=10, training iid 11–110 × 24 functions, test iid 1–10 × 24 functions, budget 1000·d, 31 runs, 50·d points for the features (once per instance, the same X for the original and the transformed instance), seed=42. All of them can be changed.**
Reason: with the defaults, the measurement uses the experimental settings of the paper. Matching its numbers is not required (D24).
[The instance numbers above are the defaults of BBOB. The defaults of MA-BBOB are in D45.]

**D9. The sampling for the features is uniform random sampling only. The preprocessing is min-max for value and mean rank / n for rank.**
Reason: the settings of the paper. Allowing other sampling would lead to comparisons outside the question.

## API and Types

**D10. An algorithm receives a `Problem` (the problem as one run sees it), a type separate from `ProblemInstance`, the element of an instance set.**
Reason: the budget, the seed of the run, and the record of evaluations are the state of one run and have a lifetime different from that of the description of an instance. With one type, `budget` and `seed` would be "None outside a run", and the type would be ambiguous. `Problem` also matches the terminology of IOHexperimenter.

**D11. `Problem` also has the names of IOHexperimenter (`bounds.lb` and so on). It does not have the names of COCO.**
Reason: algorithms written for IOHexperimenter run without being rewritten. The extra names take a few lines and add nothing for the user to remember.

**D12. An extractor returns only a `dict[str, float]`. The predictor receives float64 NumPy arrays (no DataFrame).**
Reason: one type each. The keys of a dict are feature names, which errors can name. NumPy arrays are accepted by every learning library.

**D13. The static type of the predictor parameter is `object`. The type is checked at run time by the pre-check.**
Reason: scikit-learn's `Pipeline` does not match a `Protocol` of `fit` / `predict` under pyright (the `available_if` descriptor). A type check must not wrongly reject a common form.

**D14. Settings are explicit keyword arguments only. There are no presets, setting objects, or `**overrides`. `result.config` is a dict, and `**result.config` runs the same settings again.**
Reason: IDE completion and type checks work. No concept is added.

**D15. There is one exception, `RubberRulerError`. Its message has three lines: what / Why / Fix.**
Reason: one exception to catch is enough for the user. The three lines show at once what to fix.

**D16. The pre-checks run automatically every time. Before the heavy computation, `run_test` checks all three inputs, `measure_performance` the algorithms, `compute_features` the extractor, and `fit_predictor` the predictor. There is no function that only checks and no argument that disables the checks.**
Reason: the most expensive failure is a mistake found after hours. Automatic checks require nothing to remember. Users of the component functions receive the same protection.

## Implementation and Operation

**D17. Only the results of runs are cached. Features are not cached. There are no functions that inspect or delete the cache.**
Reason: most of the time goes to the runs. A cache of features would need complex keys for little gain. Deleting the folder deletes the cache.

**D18. Python is fixed to 3.12.** (Revised to 3.11 and 3.12 by D27.)
Reason: the wheels of ioh 0.3.22 exist only up to 3.12. Users are not asked to build C++.

**D19. The development environment is Linux + Docker, uv, ruff, pyright, just, GitHub Actions, and pytest.**
Reason: specified by Shuhei.
[As of 0.1.0, the repository has no justfile and no Dockerfile. CI and the development checks run the uv commands directly (`implementation.md` Chapter 5); the checks still run in a Linux container on Shuhei's machine (`implementation.md` 3.8).]

**D20. The documentation of the first release is only the README and the docstrings. The README is divided into sections of the four kinds of Diátaxis.** (D42 moved how to connect each tool to `examples/README.md`.)
Reason: a documentation site adds work to build and maintain.

**D21. Reproducing the paper is out of the scope of this repository.**
Reason: the question concerns "your" portfolio, so the portfolio of the paper is not a feature of the library. The library is separated from the experimental code of the paper (D24).

**D22. The identifier of an algorithm is made not only from its source but also from its default values, closure values, the arguments of a `partial`, and the global values it refers to (recursively for the user's functions, by version for libraries). Values are encoded in a fixed form per type (no pickle). A value that cannot be identified triggers a warning.**
Reason: with the source alone, functions that differ only in values, such as `make_es(sigma)`, are confused, and old results are returned silently (confirmed on 2026-09-29). Being silently wrong is the worst outcome, so a warning is always given when the identification is incomplete.
Alternatives not chosen: hashing the bytes of cloudpickle (the same value can give different bytes, which defeats the cache); letting the user pass a version string (more to remember).

**D23. The license is MIT. The copyright holder is The University of Fukuchiyama.**
Reason: a small research library published with a paper is best served by MIT, the shortest and most widely known license. The code of the dependencies (NumPy, SciPy, and so on) is not bundled, so there is no conflict with any license. The paper is written at the university, so having the university as the copyright holder simplifies the procedure (Shuhei, 2026-09-29). Shuhei belongs to the graduate school (Graduate School of Regional Information Studies), but only the university can hold the copyright, so the name of the university is used. The English name follows the University Portrait of NIAD (https://jpcup.niad.ac.jp/institute/1229/1G15.html).
Alternatives not chosen: BSD-3-Clause (customary in scientific computing, but it differs from MIT only by one clause that forbids promotion with the names); Apache-2.0 (no need for patent clauses).

**D24. rubberruler is fully independent of the experimental code of the paper. It is built from scratch from `spec.md` alone, without reference to the research code. The derivation of random numbers (`derive_seed`) is defined independently, and matching the numbers of the paper is not required.**
Reason: Shuhei's policy (2026-09-29). The work of matching the research code and the fixed data derived from it become unnecessary, and the implementation becomes simple. The specification becomes the single source of truth. The correctness of the transformation and of the random numbers is checked by the test values of spec 6.1 and 6.3 and by property tests.
Alternatives not chosen: matching `derive_seed` and the values of the transformation of the research implementation (the research code would have to be handed over, and the library would be bound to the experimental code of the paper).

**D25. pflacco is not used as the example of a feature library.** (Revised by D29.)
Reason: the latest version, 1.2.2, pins NumPy 1.24 and SciPy 1.10 and does not work on Python 3.12 (confirmed on 2026-09-29). Examples that do not work are not published. Instead, an example connects a function of another form with a one-line lambda, using a small function that relies on no external library (spec 4.2).

**D26. The figure of the answer is written to `cache_dir`. No public name or argument is added.**
Reason: so that the result can be taken directly into slides and papers. The form of the figure is fixed in spec 3.4, and the user chooses nothing.
Alternatives not chosen: `result.plot` (removed by D2; it adds a public attribute); an argument that switches the writing of the figure (D2, D14).

**D27. Python 3.11 and 3.12 are supported (revising D18). The lower bound of a dependency is the older version of the two tested environments, and there are no upper bounds.** (The upper bound of Python was removed by D34.)
Reason: so that users of pflacco can install rubberruler into their existing environment. pflacco 1.2.2 pins NumPy 1.24.3 and SciPy 1.10.1, neither of which has wheels for Python 3.12, so the environment of pflacco users is Python 3.11. In that environment (Python 3.11, ioh 0.3.18, NumPy 1.24.4, SciPy 1.10.1, pandas 2.0.3, scikit-learn 1.2.2), the values of spec 6.1 and 6.3 (ψ(0.25, 0.5, 0.75), f_min, f̂_max, and the first points of the feature sample) were identical to the current environment with each of ioh 0.3.17, 0.3.18, and 0.3.22 (Shuhei, 2026-09-30). Python 3.10 reaches its end of support this October and is not included. uv.lock stays at the latest versions for Python 3.12 (the side of 3.11 receives the latest versions that support 3.11).
Alternatives not chosen: staying with Python 3.12 only (users of pflacco would need a separate environment for rubberruler).

**D28. `Problem` also has `state.optimum_found` of IOHexperimenter and always returns `False` (read-only).**
Reason: ModDE 0.0.4 reads `problem.state.optimum_found` in every generation and stops with an AttributeError without it (Shuhei, 2026-09-30). rubberruler does not reveal the optimal value (spec 4.1), so it does not reveal whether the optimum was reached either. Because the value is always `False`, ModDE runs until the budget is spent.
Alternatives not chosen: returning whether the optimum was actually reached (this would reveal the optimal value indirectly, and an algorithm could stop on it).

**D29. Examples with the ELA features of pflacco are published (revising D25). pflacco is not a dependency; how to install it is written in the README and `examples/modular_ela.py`.**
Reason: with D27, rubberruler installs into the environment of pflacco users (Python 3.11), so a working example can be published. Examples of ModularCMAES and ModDE are published with it, showing how to connect three tools that users often use. pflacco is not a dependency because pflacco 1.2.2 pins NumPy 1.24.3 and SciPy 1.10.1, and as a dependency it would bind every environment of rubberruler to Python 3.11 and old versions. The version of pflacco is pinned as `==1.2.2` because, without it, uv kept ioh and fell back to pflacco 0.4 (an old version that needs rpy2) (Shuhei, 2026-09-30).
Alternatives not chosen: making pflacco a dependency (the reason above).

**D30. Values of ±inf returned by an extractor are converted to NaN by rubberruler on receipt and counted in the same warning line as NaN.**
Reason: extractors often return infinity (`ela_meta.quad_simple.cond` of pflacco 1.2.2 divides by zero on the linear function f5). Most predictors do not accept infinity, and this becomes known only after all runs and features are computed. Handling it once, on receipt, takes less effort from the user than handling it in every extractor. As a value, it is the same as one that could not be computed, so it becomes NaN, and when the predictor fails on NaN, the usual guidance (the count and a `Pipeline` with `SimpleImputer`) appears.
Alternatives not chosen: having each extractor convert infinity to NaN (`examples/modular_ela.py` did so for a while); stopping with an error on infinity (the stop would come after all runs are computed, and as a feature the value is only missing).

**D31. An example with GA, PSO, and Nelder-Mead of pymoo is published. pymoo is not a dependency; for the tests, it is in the uv dependency group `examples`.**
Reason: pymoo is one of the tools that users often use. pymoo 0.6.2 installs into both environments, Python 3.11 and 3.12, without moving other versions. It passes solutions together with shape (n, d), which matches the (n, d) form of `problem(X)` (4.1). The extractor and the predictor are the same as in the quickstart, so the example works in both environments without pflacco. pymoo's CMAES is not included (it stops on its own criteria before spending the budget and ends after about 2,300 evaluations; Shuhei, 2026-09-30).

**D32. No example with DeepELA is published.** (Revised by D33.)
Reason: it is not on PyPI, and its install script removes pflacco and installs into the latest pflacco from GitHub, so the version cannot be pinned. It needs torch and lightning. The trained models handle up to d + 1 ≤ 12. The extractor of rubberruler is a function that receives (X, y), so a user who wants DeepELA can connect it (Shuhei, 2026-09-30).

**D33. An example with the features of DeepELA is published (revising D32). DeepELA is neither a dependency nor an extra; an installation from a pinned commit is written in the README and `examples/deepela.py`.**
Reason: fetched at the pinned commit c0368677461f96a17536111ee947bf111e8b8425 and placed on PYTHONPATH, it works without install.sh (the folder `deep_ela` is closed under relative imports and contains the trained models). With `torch.manual_seed(0)` before each call, the values are reproduced bit for bit on the same machine (confirmed for the 24 BBOB functions × value and rank, with 1 and 4 threads, on Python 3.11 and 3.12). Different CPUs differ by about 1 ulp of float32 (a Xeon with AVX-512 and an i7-13700F), and GPU and CPU differ by up to 9.2 × 10⁻⁶. The limitation of the large model to d ≤ 11 is handled by an extractor that stops for d > 11, which the pre-check reports before the heavy computation. Value-based and rank-based features differ strongly (mean absolute difference per function 0.20 to 0.67, comparable to the standard deviation of 0.39 between functions), so the question of rubberruler applies to DeepELA users too (Shuhei, 2026-09-30). It is not a dependency or an extra because a package published on PyPI cannot depend on a commit on GitHub. torch is not put into a uv dependency group either (`examples` is in default-groups, so a plain `uv sync` would install several GB of torch).
Alternatives not chosen: the install.sh of the repository (it removes pflacco and installs DeepELA into the latest pflacco from GitHub, so the version cannot be pinned); `pip install git+...` (the name in setup.py is pflacco, and the trained models are not installed); the medium model (ValueError at d = 10).

**D34. Python 3.11 and later is supported, without an upper bound (revising the range of Python in D27). On 3.13 and later and on Linux aarch64, pip builds ioh from source.**
Reason: the wheels of ioh 0.3.22 cover only CPython 3.9 to 3.12 on Linux x86_64, macOS, and Windows, but built from the sdist, all tests pass on 3.13 and 3.14, and the values of spec 6.1 and 6.3 and the card were the same as on 3.12 (evaluation of 2026-10-01; on GitHub's ubuntu-latest, building ioh took 281 seconds on 3.13 and 227 seconds on 3.14). An upper bound would make pip refuse even users who have a compiler. Without the upper bound, users without a compiler stop at a CMake error of ioh, so the README states that a C++ compiler and CMake are needed, that it takes about five minutes, and that otherwise Python 3.12 can be installed alongside. CI has a job with ubuntu × Python 3.14, and the built wheel of ioh is cached with the version of ioh as the key (Shuhei, 2026-10-01). The pflacco environment stays on Python 3.11 (D27).
Alternatives not chosen: keeping the upper bound and pointing to 3.12 in the README (users with a compiler could not install either); waiting until ioh publishes wheels for 3.13 and later.

**D35. The text that rubberruler writes is ASCII only: the card, the warnings, the messages of `RubberRulerError`, and the record of a run (the plan line, the lines of the stages and their progress, and the messages to the logger). R² is written `R^2`, and the separator of the conditions on the card is `, `. The docstrings of the public functions are ASCII too. The decorations that rich draws (progress bars, spinners, check marks, and the borders of the panel) may use non-ASCII characters only when the encoding of the output is UTF-8; every output in another encoding is ASCII only.** (Revised on 2026-10-14; the first version made every character that rubberruler writes ASCII.)
Reason: on Japanese Windows (cp932), when the output is sent to a file or a pipe, as in `python run.py > out.txt`, Python writes stdout in cp932, so the `R²` and `·` of the former card raised UnicodeEncodeError, and the answer was lost after an hour of computation (evaluation of 2026-10-01; the same on Linux with `PYTHONIOENCODING=cp932`). It can also happen with other encodings, such as Chinese GBK. Not failing is better than recommending the UTF-8 mode (Shuhei, 2026-10-01). The separator `, ` reads like an English enumeration, and a `,` left at the end of a broken line shows that the line continues. Docstrings are treated the same way because `help()` writes them to stdout (the docstrings of scikit-learn also write `R^2`). Names given by the user (algorithm names, feature names) are written as they are.
Reason for the revision: with 0.1.0, Shuhei replaced tqdm with rich for the output on stderr and added the panel of `rich.print(result)`. rich draws its decorations with non-ASCII characters only when the encoding of the console starts with `utf`, and falls back to ASCII otherwise. The purpose of D35, that sending the output to a file on Japanese Windows does not fail, therefore still holds: the quickstart in strict cp932, with the output redirected to files and in a cp932 terminal, wrote only ASCII (`implementation.md` 3.11). The rule now covers the text of rubberruler, and the decorations of rich may use their characters in UTF-8 (Shuhei, 2026-10-14). `tests/test_encoding.py` (a whole run in cp932, written to pipes) and `test_a_terminal_without_unicode_gets_ascii` in `tests/test_console.py` (a strict cp932 terminal) keep every output that is not UTF-8 in ASCII.
Alternatives not chosen: recommending `PYTHONUTF8=1` in the README (users who do not read it would fail); replacing only the characters that cannot be written (the card would change with the environment); the separator ` | ` (it looks like a table rule). For the revision: configuring rich to draw only ASCII (terminals and notebooks in UTF-8 would lose the drawing without any gain in robustness).

**D36. If the larger R² on the transformed test instances is below 0.1, the card adds two lines stating that the answer is weak and that the extractor and the predictor should be revised first. The answer is still given.**
Reason: even when both R² values were close to 0, the card stated its answer in the same tone (in the evaluation of 2026-10-01, the card of P1 was rank 0.05 > value −0.04). If the predictor explains almost none of the performance with either feature type, the extractor or the predictor should be fixed before choosing between value and rank. As in D5, the answer is given with an added caution (Shuhei, 2026-10-01). 0.1 is the level at which the predictor explains less than a tenth of the variation of the performance. The R² values of the evidence are on the second line, so the numbers are not repeated. The first version was one line (`Both R^2 are below 0.1: this answer is weak; check the extractor and predictor.`), but R^2 was not in the plural, so it became the two lines `Both R^2 values are below 0.1, so this answer is weak.` and `Check the extractor and the predictor first.` (Shuhei, 2026-10-01).
Alternatives not chosen: giving no answer (what happened would be hidden); making the threshold an argument (D2, D14).

**D37. The run of the pre-check runs in another thread of this process, and the calling thread waits up to 60 seconds. The time limit applies on every OS, from every thread, for every `n_jobs`, and to algorithms that cloudpickle cannot serialize.**
Reason: previously, `signal.setitimer` was used only in the main thread on POSIX, so on Windows an algorithm that did not end stayed stuck without any message (evaluation of 2026-10-01). Shuhei's conditions were that the limit applies with `n_jobs=1` and to algorithms that cloudpickle cannot serialize (2026-10-01). Running in another process sends the algorithm by pickle and does not meet these conditions. Another thread of the same process needs nothing to be sent, and the calling thread can return after 60 seconds even if the algorithm is stuck inside C. A thread cannot be stopped from outside, so after the limit, the `problem` of that run raises an exception at its next evaluation, and an exception is also sent to the thread with `PyThreadState_SetAsyncExc` (it arrives at a boundary between Python instructions). A long call inside C does not stop until it returns, but the thread is a daemon and does not prevent the exit. The calling thread checks the time every 0.1 seconds, so Ctrl-C also arrives at once on every OS. [Verified] On Windows (uv's CPython 3.12) and Linux, an algorithm that never ended became a RubberRulerError after 60.0 seconds, and Ctrl-C during the pre-check arrived within 0.4 seconds and stopped the thread of the run too (2026-10-01). [Verified] An algorithm that sleeps inside C without ever evaluating (`lambda problem: time.sleep(3600)`) does not receive the sent exception, but on both Linux (Python 3.12) and Windows (uv's CPython 3.12), a RubberRulerError came 60.1 seconds after the call of `run_test`, the process of the script ended 0.1 seconds later, and nothing remained (2026-10-01). Without the daemon flag, the process would not end for an hour after the error. In a process that continues, such as Jupyter, the thread keeps sleeping in the background (stated in spec 5.5).
Alternatives not chosen: running in another process (an algorithm that cannot be pickled cannot be sent; on Windows, starting a process takes several seconds); a separate mechanism only for Windows (the behavior would differ by OS); running in the calling thread and stopping it from another thread (`_thread.interrupt_main` reaches only the main thread, and neither variant can return while the algorithm is inside C).

**D38. Before the features are passed to the predictor, values in each column that differ only by rounding are unified. Two values a and b are unified only if `math.isclose(a, b, rel_tol=1e-9, abs_tol=1e-12)`. The values unified at fitting are remembered, and values at prediction are moved to the same values (spec 6.6).**
Reason: in the evaluation of 2026-10-01, R² of the rank row of the quickstart differed in the third decimal place between Python 3.11 and 3.14 on CI and 3.12 (the value row was identical to the last digit). The cause was that the skewness of the rank-based y, mathematically 0 on the instances without ties in y (2,760 of 2,880, all except f7), took scattered values of about ±1.3 × 10⁻¹⁵ by rounding, and the result of the random forest depended on the order of these values (merely permuting the same values between instances changed R² in the third decimal place; scikit-learn's trees do not split between values closer than 1e-7, but the order matters). The version of NumPy (2.4.6 on 3.11 and 2.5.3 on 3.12) and the CPU changed the pattern of rounding and thus R². Unifying only the column of the skewness made the tables of 3.11 and 3.12 identical to the last digit; the column of the kurtosis (on all functions except f7, the excess kurtosis of the ranks 1 to 100, −1.20024) collapses to one value in float32 and had no effect. After the fix, the tables of 3.11, 3.12, and 3.14 were identical to the last digit (on the development machine; 3.14 was already the same as 3.12 there before the fix, so the difference on CI appears to come from the CPUs of the runners). Shuhei's proposal (make a column exactly constant when its range in training is only of the order of rounding; fix it on the side of rubberruler, as in D30; Shuhei, 2026-10-01) does not apply to this column as it is, because the 120 instances of f7 have other values. The same idea was therefore extended to pairs of values within a column (if all values of a column are close to the smallest value, the column becomes constant, as in the proposal). Closeness is decided by the two values alone (Shuhei, 2026-10-01). The tolerance does not depend on the values of other instances, and a single outlier does not unify the other values. rel_tol of 1e-9 is Shuhei's choice: six orders of magnitude above rounding (about 10⁻¹⁵) and far below meaningful differences (in the value-based features of the quickstart, no values other than exactly equal ones were unified). Values around 0 (±1.3 × 10⁻¹⁵ in the rank-based skewness of the quickstart) are not unified by a relative tolerance, so abs_tol of 1e-12 unifies them. X lies in the search range and y in [0, 1], so a feature with meaningful differences below 1e-12 is unlikely. For tree-based predictors, the order of the unified values does not depend on the machine, and neither does the result. The change can change the answer, but only where rounding decided it (the card of the quickstart did not change). [Verified] After the rule that decides closeness value by value, the number of unified values in the quickstart was the same as with the rule based on the maximum of the column (on the 2,400 training instances, the rank-based skewness went from 1,327 values to 101 and the kurtosis from 115 to 101; no other column was unified), and the table was identical to the last digit on 3.11, 3.12, and 3.14 of the development machine and on 3.11 (AMD EPYC 7763), 3.12 (AMD EPYC 9V45), and 3.14 (AMD EPYC 7763) of CI, and the same as before the fix (2026-10-01). [Verified] For the 55 features of pflacco (d = 10, 24 functions × instances 11 to 15), the 111 values unified for value were all rounding differences with a relative difference below 1e-14 (such as 0.07400000000000001 and 0.074 for the misclassification rate of ela_level). The number of unified values was the same as with the rule based on the maximum of the column. The rank-based `ela_distr.skewness` was noise around 0 for all 120 instances (absolute values at most 1.2 × 10⁻¹⁵). With the rule based on the maximum of the column, the tolerance became about 10⁻²⁴, and 35 values remained; with the rule on pairs of values, abs_tol unified them into one (2026-10-01).
Alternatives not chosen: a tolerance of "the maximum absolute training value of the column × 1e-9" (the first version; a single outlier decides the tolerance of the whole column. `ela_meta.lin_simple.coef.max_by_min` of pflacco is a ratio of coefficients, so one instance with a smallest coefficient close to 0 gives about 1e12, the tolerance becomes 1e3, and all other values (median 28, maximum 3.9e3) collapse to one, which removes the feature. The same happens with an extractor that returns a large finite value such as 1e300 on failure. In the 55 features of pflacco (d = 10, 24 functions × 5 instances, value), the outliers were still small, and no column was broken; Shuhei, 2026-10-01); unifying only when the whole column is constant (the rank-based skewness of the quickstart is not constant because of f7, so it would have no effect); rounding values to a fixed number of digits (values near a boundary round to different sides on different machines, and values that need no unification move too); only warning (the table would still change with the machine).

**D39. psutil 7.2 is a dependency. rubberruler does not import it, but joblib (loky) uses it to stop the workers on Ctrl-C.**
Reason: loky removes the tree of workers with psutil and falls back to `pgrep`. In an environment with neither (such as python:3.12-slim, a container without procps), the fallback fails on a bug of loky (Popen has no kill), the workers block while sending results that are never read, and the process never ended (2026-10-01, confirmed with py-spy). With psutil, the process stopped 0.3 seconds after Ctrl-C even without procps, and no workers remained. psutil has abi3 wheels for Linux (x86_64 and aarch64), macOS, and Windows and installs on every Python version (Shuhei, 2026-10-01). The lower bound follows the policy of D27: the version in the tested environments (7.2.2). uv.lock changed no other version. procps was removed from the Dockerfile because it was no longer needed.
Alternatives not chosen: closing the executor in rubberruler when stopping (the way loky stops relies on pgrep itself, so closing fails at the same place); pointing to procps in the README (users who do not read it would get stuck).

**D40. The pre-check of the extractor runs on the first instance of each function (in `run_test`, the first training instance of each of the 24 functions), for both value and rank.**
Reason: previously, it ran on one instance only (f1), so an extractor that fails on some functions (`calculate_ela_level` of pflacco raises an exception on the steps of f7 at d = 2) stopped at the stage of the features, after all runs were done, and the features computed so far were lost (P3 of the evaluation of 2026-10-01; features are not cached; D17). The 24 BBOB functions all have different shapes, so one call per function finds most failures that depend on the shape of a function before the heavy computation (D16). There are 48 calls: instantaneous for the extractor of the quickstart and about 20 seconds for pflacco (about 0.4 seconds per call). An extractor that fails on only some instances of a function (P3 failed on the third training instance of f7) is still not found.
Alternatives not chosen: turning an exception of the extractor into NaN and a warning per instance and continuing (an extractor that fails would silently produce an answer, against the policy of stopping and fixing; D16, D22); checking all instances in advance (the same as computing the features twice).
[On MA-BBOB, which has no function ID, the pre-check runs on the first 24 training instances instead (D45).]

**D43. One public function is added: `rr.transform_objective`. It applies a random strictly increasing transformation with the ψ of spec 6.3 to any objective function, not only BBOB (10 public names, revising D2). This function is the only addition.** (D45 adds `rr.ma_bbob_instances`.)
Reason: it is a tool for acting on the answer of the card. A user who wants to keep value-based features even when the answer is rank can enlarge the training data with transformed objectives of their own training problems (data augmentation; requested by Shuhei, 2026-10-14). It uses the ψ of spec 6.3 as it is and creates no new transformation family, so the addition to "the smallest library that answers one question" (D1, D2) is limited to one name. `transform(instance)` receives a BBOB `ProblemInstance` and returns a `ProblemInstance`, so inputs of another type are not accepted under the same name, and the function has its own name (D3). `seed` is a required argument without a default (with a default, `[rr.transform_objective(f, lb, ub) for _ in range(10)]` would return the same transformation 10 times). As in the formula of the paper, the values are returned on the scale rescaled to [0, 1] by f̂_min and f̂_max, and z ≤ 0 and z ≥ 1 map by the identity (spec 6.7). The `transform` of BBOB clips z < 0 to 0 in step 7 of spec 6.3, which differs slightly from the formula of the paper, but on BBOB f_min is the true minimum and z < 0 occurs only by rounding, so `transform` stays as it is to keep the results unchanged. The returned function is an instance of a private class, not a closure, so that it can be pickled if `objective` can (for parallel use with joblib and similar tools). `n_samples` is an argument for objective functions that are expensive to evaluate, with the default of 10,000, the same as for f̂_max of BBOB. [Verified] In Shuhei's prototype (Rastrigin, d = 5, seed = 0), g was strictly increasing at the 200,001 points y ∈ [−50, 400] (including the sides z ≤ 0 and z ≥ 1) and continuous at z = 0 and z = 1. The true optimum (f = 0) is better than the smallest value of the sample, so it falls on the side of the identity with g ≈ −0.10. The values evaluated together with shape (n, d) were identical to those evaluated one point at a time, and also after a round trip through pickle (2026-10-14). The implementation (with the key `"objective"`) was also strictly increasing at the same points, with f̂_min = 17.84, f̂_max = 182.1, and g(0) = −0.109.
Alternatives not chosen: a procedure that enlarges a training set as a whole (such as a function that multiplies instances) and other transformation families (out of scope; spec 1.3); letting `transform` also accept an objective function (two types of input; D3); a default for `seed` (the same transformation would repeat, as above); returning the transformed values on the original scale (the scale would differ from the formula of the paper).

**D44. In the pflacco environment, pyarrow is kept below 26. pyproject has no upper bound (spec 7.3); the pflacco job of CI and the install commands for pflacco in `examples/` (three places in `examples/README.md` and the docstring of `modular_ela.py`) state `"pyarrow<26"`, with one sentence giving the reason.**

Users who install 0.1.0 together with pflacco are affected in the same way. In environments with NumPy 2, pyarrow 26 works, and an upper bound in pyproject would block those users too, so the version is pinned only in the affected pflacco environment (Shuhei, 2026-10-14).
Alternatives not chosen: `pyarrow>=25.0,<26` in pyproject (users with NumPy 2 could not use pyarrow 26 either, against the policy of no upper bounds in spec 7.3); pinning only in CI (users who follow the installation instructions would get stuck).

**D45. rubberruler also answers on MA-BBOB, through `suite="ma-bbob"` of `run_test` and the public function `rr.ma_bbob_instances` (11 public names, revising D2, D43, and the scope of spec 1.3). Everything on BBOB stays as it was: the default suite, the defaults of the instance numbers, the keys of the random numbers, the instance ids, and the card.**
Reason: MA-BBOB, the affine combinations of the BBOB functions in ioh, gives many more distinct instances than the 24 functions of BBOB, and users of algorithm selection train on it (requested by Shuhei, 2026-10-19). The question of rubberruler is the same on MA-BBOB, and ioh provides it in every supported version, so it needs no new dependency. The choices, all made by Shuhei on 2026-10-19:
- The API: `run_test(..., suite=...)` with `"bbob"` (the default) or `"ma-bbob"`, and `rr.ma_bbob_instances` next to `rr.bbob_instances`, which stays unchanged. Each component of instances has one suite in its name.
- The instance numbers stay sequences of numbers. `range` expresses the size of each set and any split, so no argument for counts is added (it would be a second way to say the same thing). The defaults of MA-BBOB are 1 to 2400 for training and 2401 to 2640 for test, the same numbers of instances as the defaults of BBOB (24 × 100 and 24 × 10). In `run_test`, the default of both arguments is `None`, which takes the default of the suite. This is the only exception to one type per input (D3): the defaults of BBOB (11 to 110 and 1 to 10) carry no meaning on MA-BBOB, where they would give 100 training and 10 test instances. `result.config` holds the numbers actually used, so `**result.config` repeats the call.
- `function_id` is `None` on MA-BBOB, which has no function ID (one instance combines several BBOB functions). The value 0, the `problem_id` of ioh, could be taken for a function and grouped silently with others (D22: being silently wrong is the worst outcome).
- The instance keys of the random numbers are `"ma-bbob", instance_number, dimension`, and the ids are `mabbob_i{instance_number:03d}_d{dimension}`. Neither overlaps with BBOB, so the random numbers, the runs, and the cache of BBOB do not change, and the version of the cache format stays the same.
- The pre-check of the extractor runs on the first 24 training instances of MA-BBOB, the same number of calls as on BBOB (D40), because there is no function to take the first instance of.
- One `run_test` uses one suite. Training on one suite and testing on the other asks a different question (generalization between suites). The component functions accept instances of either suite and do not check that one call uses one suite, so that their design stays as it was.
- The version becomes 0.2.0. MA-BBOB adds a feature and changes no answer for the same inputs, so its entry in CHANGELOG.md does not start with **Can change the answer** (spec 7.3). Under Semantic Versioning, a new feature raises the minor version.
[Verified] In ioh 0.3.22 (Linux, Python 3.12; 2026-10-19), `ioh.problem.ManyAffine(instance=i, n_variables=d)` creates MA-BBOB from the instance number alone. ioh registers it under no `ProblemClass` (`ioh.get_problem("ManyAffine", ...)` raises ValueError). The source of ioh v0.3.22 (`include/ioh/problem/bbob/many_affine.hpp`) draws the weights from the bbob2009 generator of ioh with the seed 2000 + i (24 uniform values; the two largest raised to at least 0.85, those below 0.85 set to 0, and the rest normalized), x_opt with the seed 1000 + i (uniform in [−4, 4]^d), and gives every component function the instance number i. The weights did not depend on d (d = 2, 10, 20). The value is 10^(10 Σ wᵢ (log₁₀ clip(fᵢ − fᵢ*, 10⁻¹², 10²⁰) + 8)/sᵢ − 8), and `optimum.y` is the value at x_opt. Because of the clamp, no point has a smaller value: 10,000 points around x_opt and 20 runs of Nelder-Mead gave none below it, and over instances 1 to 2640 at d = 10, `optimum.y` lay from 5.3 × 10⁻¹³ to 7.5 × 10⁻¹¹. The values of instances 1, 2, 3, 100, 2401, and 2640 were identical bit for bit with ioh 0.3.17, 0.3.18, and 0.3.22, and the test values of spec 6.1 and 6.3 were identical with Python 3.11, NumPy 1.24, SciPy 1.10, and ioh 0.3.17. A batch of shape (n, d) gives the same values as single points. At d = 1, `optimum.y` is NaN (rubberruler requires d ≥ 2). On Windows, the test values held within their tolerances in CI; on macOS, they have not been checked yet (`implementation.md` 3.1). One evaluation took about 16 µs against 0.7 µs for BBOB f1 (10,000 points together: 155 ms against 3.8 ms), so the runs on MA-BBOB take longer: with the default settings, the quickstart with `suite="ma-bbob"` took 2 hours 11 minutes with 16 workers, against about 57 minutes on BBOB (`implementation.md` 3.7).
Alternatives not chosen: `bbob_instances(suite="ma-bbob")` (the name would contradict the content); renaming `bbob_instances` to `instances(suite=...)` (an existing name would change); the defaults of BBOB on MA-BBOB, or no default on MA-BBOB; arguments for the numbers of instances; `function_id = 0`; the pre-check of the extractor on one MA-BBOB instance; a mixture of suites in `run_test`.
